# INTER-LAN Work-Package JSON Import Contract

Status: design specification.

## 1. Purpose

The Technical Lead must be able to create structured work packages from declarative JSON generated by ChatGPT or another planning tool.

The import feature exists to reduce repetitive manual data entry while preserving Technical Lead authority.

AI-generated JSON is **input data**, not executable authority.

## 2. Lead creation modes

The native Technical Lead application should support:

- Guided Form
- Import JSON File
- Paste JSON

All three modes should converge on the same validated draft model.

## 3. Versioned schema family

Initial schema identity:

`interlan.work-package.v1`

Future compatible schema families may include:

- `interlan.project.v1`
- `interlan.rework.v1`
- `interlan.regression.v1`
- `interlan.validation-plan.v1`
- `interlan.phase-close.v1`

Unknown schema versions must fail closed with a clear validation message.

## 4. Declarative-only rule

Imported JSON may describe business/workflow intent such as:

- create a draft work package;
- assign staff;
- define source identity;
- define scope;
- define requirements;
- define deliverables;
- define acceptance criteria;
- define validation requirements;
- define routing metadata;
- define closure/evidence expectations.

Imported JSON must **not** provide arbitrary shell commands, scripts or executable code that INTER-LAN automatically runs.

Fields resembling unrestricted command execution should be rejected or treated as inert text according to explicit schema rules.

## 5. Import authority flow

```text
JSON file / pasted JSON
        |
        v
Parse
        |
        v
Schema validation
        |
        v
Semantic validation
        |
        v
Preview + warnings
        |
        v
Technical Lead confirmation
        |
        v
Create DRAFT transaction
        |
        v
Audit event
        |
        v
Separate AUTHORIZE action
```

Import does not directly create an `AUTHORIZED` package.

The Technical Lead must review the normalized preview and explicitly authorize the package.

## 6. Minimum semantic validation

The importer should validate at least:

- schema/version supported;
- work-package ID syntax;
- work-package ID uniqueness/collision policy;
- referenced project/feature existence or explicitly requested draft creation;
- assigned staff exists and role is compatible;
- phase/layer values are supported;
- repository identity is structurally valid;
- source branch/source SHA fields are present when required;
- source SHA verification state is explicit;
- owned scope is structurally valid;
- prohibited scope is structurally valid;
- no direct owned/prohibited conflict unless explicitly flagged for Lead resolution;
- required validation gates are compatible with layer/type;
- acceptance criteria are non-empty where required;
- forbidden executable-command fields are absent;
- no illegal workflow transition is requested.

## 8. Import preview

Before draft creation, the native client should render a normalized preview containing at least:

```text
Project
Work Package
Feature
Phase / Layer
Assigned Developer(s)
Repository
Source Branch
Source SHA
Requirements count
Acceptance criteria count
Owned scope count
Prohibited scope count
Validation requirements
Screenshot/evidence requirements
Warnings
```

Representative warning:

`Source SHA has not yet been independently verified against the configured repository.`

Actions:

- Cancel
- Import Draft

Authorization is a later explicit action.

## 9. Source verification

Where repository integration exists, INTER-LAN should be able to verify that:

- repository exists/is reachable under configured credentials;
- branch exists when required;
- exact SHA exists;
- branch/SHA relationship matches the declared package state where policy requires it.

If live verification is unavailable, the package must record that source verification is pending rather than pretending it succeeded.

## 10. Transactional import

Import should be atomic.

Either the complete normalized draft graph is created, or no partial package remains.

Associated draft records may include:

- project/feature linkage;
- work package;
- assignment;
- requirements;
- acceptance criteria;
- scope boundaries;
- validation policy;
- routing metadata;
- initial audit event.

## 11. Audit requirements

Record at least:

- importer identity;
- timestamp;
- schema version;
- source method (file/paste/guided form);
- hash of imported JSON payload or normalized canonical representation;
- validation result;
- warnings;
- resulting draft work-package ID;
- later authorization actor/time.

Do not store secrets merely because they appeared in an imported payload. Secret-looking fields should be rejected/redacted according to policy.

## 12. AI-assisted operating model

Expected flow:

```text
Technical Lead requirement
        |
        v
ChatGPT planning
        |
        v
interlan.work-package.v1 JSON
        |
        v
Import/Paste
        |
        v
Validate + Preview
        |
        v
Lead confirms DRAFT
        |
        v
Lead AUTHORIZE
        |
        v
Developer receives work
```

The AI accelerates planning and data entry. It does not bypass Technical Lead review, repository verification, gate ownership or final acceptance.
